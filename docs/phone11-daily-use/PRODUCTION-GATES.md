# Phone11: long-call licensing and background incoming-call commissioning

Updated 11 September 2026 against official vendor documentation and the current disabled source candidate. This document separates missing implementation from provider/account configuration and physical acceptance. It contains no keys and does not report a purchase, vendor contact, APNs activation or production readiness.

The working preview remains an audio-only, single-call app. A successful foreground call does not prove locked/background delivery. The current trial has a 60-second call limit; the new optional license configuration described below has not been exercised with a purchased valid license.

## Siprix commercial prerequisite and prepared implementation

Siprix's sales page describes a one-time fee, selected platforms/features and three months of included technical assistance and updates; six- and twelve-month support options are offered. The page provides a quote form rather than a published numeric price. Platforms include iOS and Android, and the form distinguishes video, multiple calls and multiple accounts. The license is granted to the purchasing company and is non-transferable. These are the vendor's published terms, not a completed Phone11 quotation. [Official purchasing page](https://www.siprix-voip.com/contact-sales/)

A concrete quote brief, ready for the owner to use later: Phone11 is a React Native business phone app with a native Siprix bridge, initially shipping iOS voice calling and subsequently Android. Quote iOS voice now and an iOS+Android option, explicitly identify whether consultation/attended transfer and call waiting require the multiple-call option, and quote three versus twelve months of updates/support. Confirm production redistribution, existing pinned SDK compatibility, license delivery/rotation, and any application identifier requirements. There is no reason to buy video merely because the current interface once displayed a video button. No form or email has been submitted.

## Background incoming calls: integrated source candidate, commissioning still open

Apple's model uses a native `PKPushRegistry` token, APNs delivery, immediate CallKit reporting and then connection to the call service. Ordinary Expo notification tokens are not VoIP PushKit tokens. [Apple PushKit overview](https://developer.apple.com/documentation/PushKit)

The repository currently has CallKit audio/call handling, authenticated push-registration/trigger boundaries and truthful provider failures. It does **not** have a commissioned end-to-end background call path.

## Minimum acceptance before claiming daily-use production

1. **Long calls:** on a signed licensed build, place one incoming and one outgoing consenting test call on Wi-Fi and cellular. Each must cross 90 seconds and then ten minutes with clear two-way audio and working End call from either endpoint. Record SDK/build version, absence/presence of trial notification, actual duration and terminal reason. Test credential rejection explicitly without asserting that any string is valid.
2. **Background/locked calls:** use the actual assigned public number, not only direct echo. Repeat while app foreground, background for five minutes, and locked for five minutes, on Wi-Fi and cellular. Observe ring, Answer, intelligible audio, End, one Recents entry and no leftover server call. Repeat decline and no-answer.
3. **Cold start and interrupted signaling:** test OS-reclaimed app, reboot followed by first unlock and relock, and reboot before first unlock. Treat user force-quit separately and document observed OS behavior. Answer before SIP is ready; cancel from the caller before/after the wake; deliver duplicate/stale payloads; temporarily remove network. No ghost call or premature “connected” state may remain.
4. **Token/owner lifecycle:** rotate a token, restart the gateway, revoke the extension, sign out and change accounts/workspaces. Old bindings must not wake or reveal caller data to the next account. Confirm wrong-topic/environment failures produce a useful operational error and no fake success.
5. **Evidence chain:** keep a sanitized correlation from provider acceptance to native push callback, CallKit presentation, SIP/SDK session, actual audio and termination. Do not put credentials, raw tokens or full signaling captures in this public repository. The release record must distinguish code tests, deployment, provider acceptance and physical handset acceptance.
