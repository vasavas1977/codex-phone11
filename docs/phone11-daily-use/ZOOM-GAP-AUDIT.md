# Phone11 daily-use audit against Zoom Phone and Zoom Chat

Audit date: 10 September 2026. This is the source baseline at the start of the daily-use work, before the fixes being developed in parallel. It is not a release certificate. The current implementation report should identify which gaps have subsequently closed.

## What “usable like Zoom” means

The first milestone is dependable calling and real team messages: sign in once, receive a call without opening diagnostics, answer and end it, call a colleague, exchange a persistent message, see accurate unread counts, and recover clearly from failure. Zoom's current mobile guide supports the phone, chat, contact and search workflows described here. Full feature parity is a larger product, not a prerequisite for the first useful pilot. [Zoom mobile guide](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0063582)

Evidence levels are kept separate: implemented source, automated tests, deployed server, signed installed app, and physical acceptance. A mock screen or successful SDK command is not evidence that a person received a call/message.

Known physical evidence from this task: build 13 received the direct incoming echo test with ringing and clear echo; the user confirmed that End call disconnected immediately, and the parent task reported server confirmation that the handset ended the call before the guard timer. Earlier outbound PSTN testing had clear two-way audio and saved history. Incoming public-number routing is still unverified end to end. Locked/suspended/terminated incoming delivery, Android, Bluetooth, long calls, and a second chat recipient have not been accepted. The current Siprix trial is limited to 60-second calls; a paid production SDK license is not established. Historical May handoff claims must not override these narrower observations.

## Executable acceptance plan

The following source checks can be run now from the repo root. They are regression checks, not proof of carrier, push, audio, chat delivery or deployment.

```sh
./node_modules/.bin/vitest run tests/phone11-current-call.test.ts tests/phone11-current-call-banner.test.tsx tests/phone11-siprix-callkit.test.ts tests/phone11-siprix-engine.test.ts tests/phone11-call-history.test.ts tests/phone11-dial-input.test.ts
./node_modules/.bin/vitest run tests/phone11-auth-sip.test.ts tests/phone11-siprix-selection.test.ts
EXPO_PUBLIC_SIP_ENGINE=siprix EXPO_NO_TELEMETRY=1 ./node_modules/.bin/expo export --platform ios --output-dir /tmp/phone11-daily-use-audit-export
```

Run the new directory/chat/readiness tests introduced by the implementation lanes as well. Do not accept old presence/demo tests as evidence of a live service. The baseline has pre-existing repository-wide TypeScript errors; changed-file checks and export success must be reported separately from full typecheck success.

Physical and server checks should be performed as these repeatable scripts, with a build ID, sanitized call/message ID, time, outcome and failure reason recorded for each run. Use consenting test endpoints; the agent must not call arbitrary customers or send test messages to real colleagues without authorization.

1. **A01 / A18: startup and account lifecycle.** Launch signed app with an existing enabled account. It becomes ready without opening Diagnostics. Repeat after an ordinary app restart and after airplane mode off/on. During a directory/message load, sign out and sign in as test user B; no user A data appears. Revoke the session; a clear sign-in path appears without losing the user's unsent draft to an unrelated user.
2. **A02 / A03: incoming matrix.** Call the assigned public DID from an external test phone with Phone11 foreground, background for five minutes, and locked for five minutes, on Wi-Fi then cellular. For each state answer, speak both ways, end from Phone11, repeat ending from the caller, and repeat Decline/timeout. Confirm one terminal history row and no orphan server call. Termination by the OS and user force-quit are separate cases; record actual behavior rather than promising both are equivalent.
3. **A04 / A08: controls.** During a live test, minimize and reopen the call; End stays reachable. Mute produces silence at the other endpoint, unmute restores voice; hold/resume restores voice; DTMF selects a known test IVR choice; route audio between earpiece, speaker and paired Bluetooth. Inject a rejected SDK command; UI must retain the real call with an error and retry path. No state change may be inferred solely from a button tap.
4. **A07: duration.** On a production-licensed build, sustain a 10-minute physical call and a representative longer call, including a network transition. Confirm no trial cutoff, intelligible audio and correct final duration. The trial build cannot pass this criterion.
5. **A05 / A14 / A15: two-person chat.** Use two authorized test users A/B in one tenant and C in another. A creates a DM with B and sends a unique Thai/English message. B receives it exactly once; reopening/relaunching preserves it. Before opening, B's unread badge increments; opening clears it and persists across restart. Disconnect A during send, retry after reconnect, verify one server message. C cannot fetch/search/send/read/mutate that conversation by guessing its ID. Test revoked membership and device logout while a request is in flight.
6. **A09 / A16: directory/search.** Search actual test names in Thai and English and an extension with separators; tap Call and verify one real call request, then a real ringing/connected screen. Search an absent name and simulate HTTP failure: distinguish No results from Could not load. No fake people or availability are shown in either state. Verify one tenant cannot enumerate another.
7. **A11 / A12: history and voicemail.** Place answered, declined, canceled and unanswered tests. Restart the app and confirm each outcome and duration. Leave a known spoken voicemail at a test extension; only its owner or explicitly authorized delegate can list, stream, mark read or delete it. Stop playback on navigation/logout. A missing/expired audio URL displays a retryable error, never a fake progress bar.
8. **A13 / A19: later PBX features.** Keep controls unavailable until three-endpoint blind and attended transfer succeed. Failed/declined consultation must return to the original caller. Set a short test business-hours rule and observe real forwarding/voicemail behavior; restore it after the test.
9. **A17: accessibility.** On the actual iPhone, use VoiceOver to sign in, search a contact, call, mute and end, read a message and reply. Increase system text size and use Thai names/messages; every primary action remains visible and understandable. Repeat key journeys on Android only after a signed Android build exists.

## Implementation sequence and external dependencies

1. Fix truthful navigation, enabled-account foreground registration, call entry points and unsupported controls. Replace mock data with a protected directory and real conversation service. These are independent implementation lanes and can ship together once their regression tests pass.
2. Deploy server/API changes and install a signed build; accept two-person persistent chat and the existing foreground calling path. Do not mistake local service tests for deployment or recipient acceptance.
3. Complete PushKit/APNs and server wake routing, durable tokens and call cancellation. Apple documents the PushKit-to-CallKit lifecycle; a generic notification token is not a substitute for a VoIP token. [Apple incoming VoIP calls](https://developer.apple.com/documentation/callkit/making-and-receiving-voip-calls?changes=__4)
4. Obtain/configure the appropriate Siprix license, prove public-number incoming calling and long-call reliability, then expand to voicemail, transfers, chat push and audio-route acceptance. Credentials, provisioning entitlements, paid license and physical endpoints are external dependencies; they cannot be completed honestly by changing a feature flag or passing mocked tests.

Research used official Zoom support/technical material and Apple documentation. It did not rely on third-party feature lists or imply Zoom's licensed capabilities are already available in Phone11. The goal is to adopt dependable user workflows, not duplicate Zoom branding or claim parity prematurely.
