# Web meeting authentication lifetime — 5 October 2026

A pending web join previously retained only a numeric account ID. Logout followed by a new same-ID sign-in before the queued join installed its owner listener could connect the old admission. The prejoin route checked the exact authenticated object before entering the lifecycle and after it returned, but initial media could run inside that interval. The source mock reproduction against `32d9af7` accepted the old token and created/connected one room after the authentication object changed.

The web lifecycle now captures the exact authenticated object synchronously and installs its own pending-owner subscription before its first await. An observed interruption permanently retires that attempt, including restoration of the same object. Stable authenticated profile refreshes retain the same object and remain valid. The temporary subscription is removed when the join settles; an established lifecycle keeps its own owner subscription until its actual cleanup succeeds.

The shared browser controller accepts an optional current-owner guard. Only the web lifecycle supplies it; existing native, desktop and generic callers retain their previous behavior when it is absent. The guard fences room creation/connect, initial microphone/camera publication, queued controls, screen capture and provider callbacks. Owner loss immediately retires the old snapshot and refuses new operations. Late connection/publication results still pass through the existing tracked disconnect barrier. A failed SDK stop retains the exact old lifecycle/room for cleanup retry and blocks replacement joining; it does not release that responsibility merely because the owner signed out. The retired lifecycle hides its public room/track view from a new same-ID UI while its controller still retains the room for teardown. Old callbacks and successful old cleanup do not clear a replacement registry entry.

This is local authentication lifetime protection, not a provider token revocation or a new meeting policy. Server membership/admission and connected SDK publication grants remain independently necessary. Browser sharing still requires an interactive admission and the connected participant's actual screen publication entitlement; screen audio remains off. No host authority, automatic join, second native audio lease, provider operation or policy switch was added.

The requested administrator-managed screen policy remains unsupported by the current released seam. [`publishScreen`](../../lib/meetings/policy.ts) has a standalone evaluator but no production storage/router consumer. The administrator page persists meeting-start eligibility only. The [`phone11-plain-video.v1` facade](../../server/meetings/connect11-plain-video-facade.ts) accepts `interactive`/`listener` plus an optional display label, and exposes no source-grant restriction or connected-permission update. [LiveKit supports authoritative `canPublishSources` grants](https://docs.livekit.io/frontends/reference/tokens-grants/), but Phone11 cannot invent a Connect11 field or control principal to enforce them. A reviewed provider contract for source-grant intersection and connected revocation, backed by authenticated tenant/admin policy storage and fresh member/revision checks, is required before presenting an enforceable admin policy. Hiding a client button or changing all media to listener is not that policy.

Validation uses actual lifecycle/controller source with mocked SDK rooms and stable authentication objects. It covers queued and network joins, same-ID replacement, same-object restoration, delayed initial microphone and screen publication, failed stop/retry, old callbacks, and unchanged web/browser/native/media-ownership regressions. It performs no browser capture, server/DB/provider mutation, app launch, SDK runtime, signing, deployment or device acceptance.
