# Browser screen publishing source candidate

Base: `acc93c2fa6ea15c4dc48e424c0624fbbf1f8a07a`. This candidate adds video-only Share/Stop to the existing authenticated LiveKit 2.22.3 web room. It creates no other room, recording, provider grant, native publisher, or desktop capture permission.

The control is available only for an explicit server-derived `interactive` admission and the currently registered authenticated web lifecycle. The connected local participant must expose the SDK capture/publication APIs and `permissions.canPublish=true`; `canPublishSources` must be empty (SDK meaning: all sources) or include the SDK's screen-share source. Missing admission profile, permissions, API, secure context, or browser display-capture support fails closed. Permission changes stop capture. This does not implement tenant `publishScreen` policy or grant host controls: the standalone policy resolver remains unconsumed in production, and admin policy switches stay unavailable.

`startScreenShare()` invokes `createScreenTracks({audio:false})` directly in the button callback before any await or media queue. The browser chooses the source. Acquired tracks belong to the session before publication, and only one live video screen track is accepted. Owner, room, generation, screen epoch, SDK entitlement, and live-track state are checked before and after publication. UI reports choosing/publishing separately; only a current live publication reports sharing.

Stop, browser track-ended, provider unpublish, permission revocation, `reconnecting`, `signalReconnecting`, owner change, and leave invalidate pending work and stop acquired tracks. Screen publication cannot restart automatically. Leave drains pending chooser/publication work and stops late results before another room can acquire capture. A browser chooser cannot be programmatically dismissed: Stop/leave remains pending until it settles, and a late chosen track is disposed without publishing. Cleanup failures retain track/room ownership for retry rather than authorizing another publisher. Existing native SIP/meeting media ownership remains intact; native and desktop screen publishing remain unsupported.

Validation uses mocks only; the test display-capture entry point throws if called. Coverage includes direct click invocation, missing/restricted grant and API capability, double start, picker denial/cancellation, unexpected audio, ended tracks, publish/stop failures, stale owner/picker/publish completions, reentrant leave, teardown retries, both reconnect events, and native/UI regression suites. No browser picker, display capture, provider request, recording, installation, or device action was performed. Green source checks do not prove browser/remote media interoperability or provider policy enforcement. Independent source review and later separately authorized browser/provider acceptance remain required.

API references: [LiveKit screen sharing](https://docs.livekit.io/transport/media/screenshare/), [LiveKit 2.22.3 participant API](https://docs.livekit.io/reference/client-sdk-js/classes/LocalParticipant.html), [LiveKit publication grants](https://docs.livekit.io/frontends/reference/tokens-grants/), [W3C Screen Capture user activation and chooser requirements](https://www.w3.org/TR/screen-capture/). Desktop selected-source permission handling is a separate slice governed by the [Electron session API](https://www.electronjs.org/docs/latest/api/session).
