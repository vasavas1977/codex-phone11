# 3001 → 1020 call investigation — 19 September 2026

## Observed failures

- User reports 1020 → 3001 works; 3001 → 1020 stays Calling on mobile data.
- Metadata-only trace at 09:37:40 UTC proves the authenticated 3001 INVITE targets 1020 and is forwarded to its registered source endpoint. The 1020 registration succeeded 11 seconds earlier. No response arrives from 1020; the transaction ends with 408 at 09:38:10 UTC.
- User then confirmed that 1020 rings on Wi-Fi. At 09:45:41 UTC the comparison trace records 180 Ringing and, at 09:45:45, 200 OK from the Wi-Fi endpoint.
- The forwarded INVITE in that comparison is 2,575 bytes over UDP. Fragmentation/network filtering is a plausible explanation for mobile-data failure, not yet proven by a handset capture. RFC 3261 section 18.1.1 recommends a congestion-controlled transport for requests over 1,300 bytes when the path MTU is unknown.
- A separate, concrete Wi-Fi dialog bug is visible: registration lookup honors the received endpoint, but the 200 OK Contact contains a different, public-looking LAN address. The subsequent ACK and BYE go to that advertised address, rather than the endpoint that answered. The 200 OK repeats and BYE times out.

## Bounded remediation

2. Test TCP provisioning for tenant 1, extension 1020 only. Preserve credentials, SRTP, account ownership, and 3001 settings. The installed native bridge already supports TCP; this is not a development-build install.
3. Verify registration, incoming ringing, answer, two-way audio, call lasting beyond 35 seconds, and hangup. Registration or parser success alone does not pass handset acceptance.
