## Loaded startup and shutdown

After listening, 3000 starts the chat alert dispatcher, chat-media retention, recording analysis, recording retention, recording capture, and the FreeSWITCH ESL listener (`/app/dist/index.mjs` lines 9770-9781). The running environment has chat notifications `1`, recording retention `true`, recording AI `true`, and cloud recording capture `true`; this is configuration evidence, not proof of current in-flight jobs. SIGTERM stops the recording/retention timers, destroys the ESL connection, calls WebSocket shutdown, and closes HTTP (`/app/dist/index.mjs` lines 9783-9792). It neither retains nor calls the return value from `startChatNotificationDispatcher()` at line 9772, and it awaits no worker completion. The dispatcher can run up to ten sends in one tick, then schedule another tick after five seconds (lines 3399-3425). An APNs alert send has a five-second transport budget (lines 3215 and 3305-3360), but this is not a whole-tick or shutdown deadline. The ESL stop only destroys its socket (lines 9624-9632); its socket-close handler can schedule a reconnect (lines 9470-9485). No loaded-bundle path was found that evicts a Connect11/LiveKit meeting room or tears down provider media. Absence in this bundle is not provider-runtime attestation and does not waive the guard.

## Durable alert state and handoff consequence

The dispatcher selects one `pending` outbox row under `FOR UPDATE ... SKIP LOCKED`, changes it to `attempted` inside the claim transaction, and returns only after that transaction (`/app/dist/index.mjs` lines 446-456). It rechecks authorization/current state before the APNs call (lines 458-461 and 3372-3384). After the provider call it updates `attempted` to `accepted` or `unavailable`, conditional on the same device revision (lines 463-465 and 3385-3395). Future claims select only `pending`; no attempted-state lease expiry or automatic retry exists in the loaded repository. `attempted` rows are eventually pruned only after expiry plus one day (lines 480-481). A changed or removed device can also leave `attempted` unchanged because `finish` requires a matching device row and revision.

Consequently, killing the process after claim and before completion leaves a durable `attempted` row. The provider might already have accepted the alert, or might never have received it; the database cannot distinguish those cases. A new dispatcher using the same pending-only claim does not duplicate-send that row, but can lose the alert. Resetting `attempted` to `pending` to recover the loss can duplicate an already accepted send. APNs uses a freshly generated request ID (line 3345), so that ID does not supply durable retry identity. Do not reset or replay attempted rows as an ad hoc handoff step.

Current bytes do not expose an in-flight dispatcher count, a retained stop handle, or an awaited drain. Pausing incoming chat mutations and observing `pending = 0` would not prove that an already claimed alert has finished; historical and in-flight `attempted` rows have the same state. The per-send APNs budget does not bound database acquisition, the full ten-item tick, or SIGTERM. Therefore a loss-free, bounded old-to-new worker drain is **not source-provable for this deployed bundle**. A reviewed handoff needs explicit admission fencing for new chat/alert work, a worker stop-and-await protocol or equivalent externally attested in-flight barrier, and a defined disposition for ambiguous attempted rows. Keep the existing 3000 maintenance/provider guard until that contract and the auth/wake/recording route continuity are implemented and independently checked. Do not infer that all provider sessions must be evicted merely from this missing worker barrier.
