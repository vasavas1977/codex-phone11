# Android screen consent transaction — 5 October 2026

This is a default-off Android source candidate. Ordinary Android and iOS screen publishing remain unsupported. Source/JVM/compiler/prebuild evidence does not establish JNI, browser/handset capture, remote video, audio exclusion on a device, signing, distribution or provider acceptance.

The pinned `@livekit/react-native-webrtc@144.2.0` bridge has an additive `phone11ScreenBegin(operation, lifetime)`, `phone11ScreenCancel(operation)` and `phone11ScreenStop(operation)` seam. Its released `getDisplayMedia`, camera and iOS implementations are unchanged. An opaque lifetime labels the original admitted lifecycle; it is not authentication, a room revision, a provider token or a publication grant. The caller must intersect the lifecycle's original observed authentication lifetime with its exact connected room, interactive admission, existing current media lease, SIP-idle state and the connected SDK screen publication permission.

Each operation requests fresh OS consent. Intent data stays in native memory and is consumed once. Process-wide operation retirement and monotonically unique Activity request codes prevent late results or module replacement from binding old consent to another attempt. Cancellation retires before queued cleanup; a pending chooser settles without waiting for its late Activity result. Only that owned consent Activity transition is exempt from native background retirement. Service startup resolves after successful `startForeground`, and the executor rechecks the operation and current foreground Activity before capture. Startup/capture errors do not report capture success. Timeouts reject rather than manufacture acknowledgment.

The strict capture path creates video only. It propagates startup failures rather than using the released controller's swallowed exceptions. Stop awaits strict `ScreenCapturerAndroid.stopCapture`, capturer/source/texture/track/stream disposal and the exact service's `onDestroy`. The pinned SDK bytecode shows that `stopCapture` synchronously releases the virtual display and stops/unregisters the projection on its texture handler; `dispose` alone only marks the capturer disposed. Stage flags retain partial resources on failure for retry. A service stop boolean, missing track lookup and JS `track.stop()` are never treated as this receipt. Duplicate stop coalesces. Native process custody survives React module replacement until acknowledged cleanup; a replacement request cannot overwrite it.

The JS adapter tracks late capture/publication results and retains cleanup when either native stop or SDK unpublication fails. Capture audio is not requested or published. Logout, reconnect, replacement, leave, SIP interruption and genuine native background loss must stop through the same barrier. A later share requires a new explicit Share action; nothing restores consent or capture from process state.

Activation requires matching `PHONE11_ANDROID_SCREEN_TRANSACTION=1` and `EXPO_PUBLIC_PHONE11_ANDROID_SCREEN_TRANSACTION=1`, plus explicit `EAS_BUILD_PLATFORM=android`. Store builds and iOS generation refuse activation. Both flags default to `0`; no environment or deployed flag was changed. The reversible plugin adds only the owned unexported projection service, native gate metadata and projection foreground permission when ON. OFF removes that owned wiring. The released library's generic `MediaProjectionService` declaration remains separate; absence of our permission does not imply that declaration vanished from a merged manifest.
