# Phone11 durable push server candidate — 10 September 2026

This is a second backend source candidate prepared after preview build `75fa3c9` was dispatched. It has not sent to APNs, changed the live database or proved background calling. The first preview build and its release evidence remain separate.

## Implemented and locally exercised

- `server/push/apns.ts` sends explicit `node:http2` POST requests to Apple's fixed sandbox/production hosts, using TLS ≥1.2, VoIP topic/type, priority 10, expiration 0 and a request UUID. Server configuration locks topic/environment; client metadata must match. Ordinary APNs alert tokens cannot be sent as VoIP tokens.
- Auth uses a P256 private key with ES256 and a 64-byte IEEE P1363 signature. JWTs are cached for 50 minutes and concurrent initialization is coalesced. Wrong/missing key material fails without logging it. Restart the process after replacing/revoking a key at the same path so its cached token cannot persist.
- Each network attempt is bounded, with one five-second call deadline shared across devices, key loading, ownership checks, retry waits and transport. One explicit `TooManyRequests` response may be retried after its delay if the live-call budget permits. Authorization and request ID remain stable. Assignment is rechecked before every attempt. Timeouts/stream errors/GOAWAY are uncertain acceptance and are never replayed automatically. Apple's documented 15-minute 5xx retry delay is unsuitable for a current incoming call, so the call push fails instead of being queued until stale. [Apple response handling](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns)
- Structured failures separate configuration, authentication, invalid token, throttle, provider unavailability, rejection, timeout and transport errors. Untrusted response bodies, raw token values and key paths are never included in returned/logged errors. Invalid-device responses remove only the saved revision involved in that send. A newer registration or a registration newer than Apple's 410 invalidation timestamp survives an old rejection.
- `server/push/repository.ts` persists auth session/tenant/user/extension/device/platform, token/type/hash, bundle/environment, revision and timestamps in PostgreSQL. No development memory fallback exists. Authentication supplies the owner and session from the request; client input cannot select either. The registry references `phone11_auth_session(id)` with `ON DELETE CASCADE`, so durable sign-out/session revocation deletes its devices. Active, unexpired session plus enabled identity mapping and phone assignment are rechecked in the registration transaction, lookup and final attempt checks. Transaction advisory locks enforce the ten-device owner quota across processes. Token rotation replaces one device binding; the same provider token is removed from an earlier account when freshly registered by its new authenticated owner. Explicit removal requires the current user/session plus exact token/device/platform; a late request from an older sign-in cannot remove a newer binding.
- Gateway `sent` counts only a provider-accepted request. This is not phone receipt, ringing, answer or audio. Missing Apple/FCM configuration continues to return zero. `getPushStats`, `getTokensForUser` and unregister are async; current async router handlers already support their promises. The router now passes request headers internally for register/unregister; `server/push/session.ts` resolves a fresh Better Auth session and explicit active legacy-user mapping.

Connections are currently created and cleaned up per request, rather than pooled across calls. This limits resource lifetime and is appropriate to the bounded candidate; commission sustained-load pooling/circuit-breaker behavior separately before claiming scaled service reliability. Device tokens are sensitive database fields: restrict database/operator access and backups; do not expose registry rows through public APIs. Only aggregate statistics are returned by the existing admin route.

## Deployment prerequisites — not performed here

1. Independently review and apply **only** `server/push/migration.sql` to the approved owned-auth/PBX PostgreSQL database. It adds `phone11_push_devices` and a prefixed index; it does not alter users, assignments, routes or provider settings. Existing `phone11_auth_session`, `phone11_auth_identity`, `users`, `tenants`, `extensions`, `user_extensions` and `sip_accounts` must have the repository's ownership semantics. There is no automatic startup migration. Deploying this candidate before migration makes registrations fail safely.
2. Deploy the reviewed backend source. Registry rows then survive worker restarts; no in-memory registrations are migrated automatically. Clients need to register their current native VoIP token again.
3. Only when commissioning is authorized, configure `APNS_KEY_PATH`, ten-character `APNS_KEY_ID`, ten-character `APNS_TEAM_ID`, exact `APNS_BUNDLE_ID`, and `APNS_ENVIRONMENT=production|sandbox`. Use protected server storage for the Apple `.p8` key. The bundle/environment must match the signed application's native PushKit token. No credential values were inspected or added here.
4. Keep the trusted PBX trigger behind the existing `PUSH_SHARED_SECRET`/`x-push-secret` boundary. This source does not commission the proxy integration or make an inactive native PushKit feature ready.

## Remaining engineering and handset acceptance

Native PushKit token creation/invalidation, immediate CallKit reporting, cold/locked signaling credentials, push/SDK call-ID correlation, stale-call cancellation and actual proxy INVITE hold/resume are separate from this server candidate. Standard chat notifications are also separate from VoIP. The server payload remains the existing `callId`, caller fields, video flag, type and timestamp; a completed end-to-end call-status/correlation protocol must be agreed before native background commissioning.

The acceptance gate remains a signed entitled app: assigned public number → Apple acceptance → native PushKit callback while locked/background → correct-owner SIP registration and matched INVITE → Answer → clear two-way audio → End and one Recents entry. Repeat remote cancellation, duplicate/stale push, sign-out/account change and gateway restart. Provider acceptance alone closes none of those phone-side gates. See [the production gate record](PRODUCTION-GATES.md).

Logout cascade prevents future submissions after durable server revocation. A provider request already accepted before logout cannot be recalled through deletion of a registry row; the native owner/session lifecycle must also clear and reject stale pending calls. Offline local sign-out requires the device to stop its native push lifecycle and retain only safe pending cleanup metadata until the server can revoke the session.

## Final gateway deadline review

The gateway now applies its shared five-second deadline to initial assignment lookup, device lookup, final ownership checks, APNs/FCM delivery, each FCM credential-acquisition stage, accepted-delivery persistence and invalid-token cleanup. A timed-out lookup cannot resume into a later push send. Late rejections from abandoned promises remain observed. Accepted provider delivery remains counted if its timestamp persistence subsequently hangs. Tests cover hung lookups, late credential resolution, hung post-acceptance persistence and failed cleanup without unhandled rejections.

The deadline bounds the API request lifetime and stops later notification submissions. It does not cancel an already-running PostgreSQL statement: a delayed timestamp update or invalid-token deletion may finish later, but both are restricted to the original saved revision. An APNs/FCM request already submitted before the deadline may have uncertain remote acceptance; no automatic replay follows a timeout.
