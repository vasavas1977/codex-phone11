# Provisioning initializer extension tenancy — 9 October 2026

The fallback initializer previously created `extensions.tenant_id INTEGER DEFAULT 1`, nullable and without a tenant FK. Its missing-column branch could assign every existing extension to tenant1 without an explicit ownership decision. This source change removes those two creation hazards.

New extension tables require an explicit `tenant_id INTEGER NOT NULL REFERENCES tenants(id)` with no default. The FK uses PostgreSQL's default NO ACTION behavior, matching the existing legacy prerequisite. The initializer continues to use its established selected schema (`public` in production; the owned test schema in CI); other tenant-table definitions are unchanged.

For a missing tenant column, one anonymous PostgreSQL block checks the catalog, acquires an ACCESS EXCLUSIVE table lock with NOWAIT, rechecks the column, refuses any populated extension table with `55000`, and adds the hardened column only to an empty table. The empty check and ALTER share one transaction and lock, so a concurrent writer cannot add a row between them. Contention returns `55P03`; the initializer does not retry or bypass it. The refusal does not assign tenants or add the column. Earlier initializer CREATE/seed statements can already have committed; this is not a transaction around the complete initializer.

An existing tenant column is left unchanged: nullable/default1/noFK legacy state, existing rows (including NULL/orphans), and an already hardened column are preserved. Existing legacy tenancy still needs fresh operator review and the guarded prerequisite before advanced commissioning. This is not a live migration, automatic backfill, reassignment, or a repair of other tenant tables.
