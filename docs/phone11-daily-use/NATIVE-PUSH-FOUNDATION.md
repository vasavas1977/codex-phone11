# Native VoIP push foundation and integrated candidate — 11 September 2026

**The current source candidate is described in [NATIVE-WAKE-CANDIDATE.md](NATIVE-WAKE-CANDIDATE.md). Background and closed-app calling remain unavailable in the shipping configuration.** The newer implementation closes source gaps described in the original 10 September foundation; it does not establish deployment, APNs acceptance or physical locked calling. `PHONE11_VOIP_WAKE_COMMISSIONED` remains zero and `closedAppCalling` remains false.

## What is now prepared

- A process-owned PushKit registry with token rotation/invalidation and a Swift AppDelegate bootstrap before React startup. A bridge reload no longer destroys the registry. The disabled gate allocates no registry.
- Immediate generic incoming-call reporting through RNCallKeep's one existing provider. A forwarding delegate reserves one UUID, retains early Answer, handles expiry/cancel/End and forwards ordinary calls unchanged. Unknown/expired payloads fail in an isolated call; a report error never ends an existing UUID.
- A limited native incoming-wake grant in a separate `AfterFirstUnlockThisDeviceOnly` keychain item. Existing SIP password, auth bearer, device ID and revocation ledger retain their prior `WHEN_UNLOCKED_THIS_DEVICE_ONLY` policy. The grant is absent from native public binding snapshots and diagnostics. The full SIP password returned by a valid claim is held in native RAM; its residual revocation risk is explicitly documented in the candidate record.
- Native claim/ready/status/end consumers with a fixed HTTPS origin, five-second request/resource budgets, no redirects/cookies/cache reuse, setup expiry and connected-call lease heartbeats. Definitive authorization rejection ends only the owned wake; transient HTTP failure does not invent a SIP End.
- Shared Siprix runtime resume/adoption, exact `X-Phone11-Wake-ID` matching, real registration completion, Answer fulfillment only after connected, existing CallKit audio-session forwarding and bounded failed-End cleanup. JavaScript adoption revalidates the exact authenticated session/binding, not just the user/tenant.
- Authenticated register-first token rotation: persist the new cleanup evidence, register it, then unregister the old token. Same-token/device reassignment cannot accidentally unregister the new row. Server revision protection remains intact while an additive wake migration transfers a same-session binding pointer. Logout stops native work, preserves uncertain cleanup and relies on authoritative server session revocation.

## Proof boundaries

Current host-native tests execute the coordinator, process registry and shared SDK bridge with fake platform/network dependencies, and compile against installed CallKeep and pinned Siprix headers. Client tests cover exact-session adoption, owner changes, late completions, token persistence/rotation and cancellation. Server tests use synthetic data, isolated PostgreSQL and loopback HTTP/mocked APNs. These checks are not live device delivery or audio evidence.

Historical **build15**, source `ab518f6396b0141be633b7ce11ed984622ac113a`, passed the actual signed iOS build and was installed with the earlier foundation gate closed. [Historical build](https://github.com/vasavas1977/codex-phone11/actions/runs/34473813573). That result establishes linkage of the earlier foundation only, not the newly integrated wake candidate. Build19's accepted foreground direct echo is also separate from locked incoming behavior and from the reported silent public-number call.

Candidate code `54923dc` is signed as build 21; see [verified artifact evidence](RELEASE-CHECKPOINT.md#signed-and-installed-candidate-build-21). Installation and independent device inventory confirm version 1.0.0/build 21; physical call acceptance for this version remains pending. The [proxy held-INVITE/resume/cancel consumer](KAMAILIO-WAKE-CANDIDATE.md) is prepared and passed seven isolated SIP scenarios and a full private parser check against the installed binary. Remaining gates are approved migration/proxy deployment and commissioning, Apple provider configuration and physical foreground/background/locked/OS-reclaimed acceptance. Before-first-unlock and user force-quit behavior must be recorded separately. No production PushKit flag, provider credential or live PBX route was enabled by this source work.
