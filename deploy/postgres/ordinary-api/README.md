# Restricted ordinary API database role

`runtime-grants.json` is the reviewed finite operation/column inventory for the ordinary `api-candidate` backend. It covers authentication, invitations, PBX/SIP/voicemail, chat/profile/push, meetings and recording HTTP paths. It does not grant fraud policy authority or enable background workers. Source references are a navigation index: generated Better Auth SQL and dynamic PBX setter lists are explicitly covered in the manifest. Review source and update this manifest when those paths change; do not automatically grant a new table or column based on catalogue discovery.

Run `collect.sql` through the bounded Root native operator using `psql -X -qAt -v ON_ERROR_STOP=1`. It is read-only catalogue metadata, with no customer rows or credentials. Root saves actual observations outside the repository and verifies ROLLBACK. Render offline with `python3 render.py --catalog /absolute/catalog.json --mode production --out /absolute/new-directory`. The new output directory must not exist. The output is reviewed SQL, not an execution tool. The renderer also supports owned synthetic `p11_mgmt_grants_*` clones with a different cluster system ID.

The transaction creates a new NOLOGIN role and two independent ordinary audit policies, then verifies effective permissions. All initial/old API and fraud roles remain untouched. It pins current PG16.13, production database/system ID, catalogue freshness, existing columns/RLS/owned sequences and audit policy hash. It rejects persistent-schema CREATE, powerful role flags, membership, ownership, grant options, publicly executable noncatalogue SECURITY DEFINER functions, unexpected table privileges and sequence reset/read privileges. INSERT/UPDATE are granted only on enumerated existing columns. SELECT freezes existing observed columns. No default/all-table/all-sequence grants exist. Missing source columns are recorded in the render receipt rather than created; inspect those differences against enabled features before cutover.

The existing application authentication and tenant membership/predicate checks remain the authority for requests. This change provides no additional general database-level tenant isolation. Audit append additionally requires an active owner/admin actor in the recorded tenant. Ordinary audit reads rely on the existing application tenant filter. Audit mutation/truncation is denied. The canonical user role and identity mapping cannot be updated. PUBLIC TEMP may remain; role search_path `pg_catalog,public,pg_temp` puts existing persistent tables before temp relations. A trusted service login with allowed membership DML still relies on application authorization.

Run `PHONE11_GRANTS_PG16=1 python3 test_grants.py` for the exact local PG16.13 ACL/RLS/TLS/SCRAM suite. It requires the preexisting image digest in the test source and native psql/openssl; it never pulls an image. Every fixture has an ephemeral loopback port, tmpfs data, private generated synthetic password/certificate, database/role-specific /32 HBA and exact-ID/name/nonce cleanup. A default run uses local PostgreSQL17 as supplementary coverage. The fixture shape tests ACL semantics, not handler/business constraints. The owned synthetic runner `RUN-EXACT-GRANTS-HTTP.py` in the external operator packet exercises actual HTTP auth/context, invitations and routing transactions with this exact rendered grant manifest. It complements the native ACL/TLS suite; it does not prove production signed-in acceptance. The ordinary tRPC route was switched before a combined exact-grant HTTP rehearsal was available; that original sequencing gate was not met. A later synthetic rehearsal closes the source/grant integration gap only. Fresh owner-authorized signed-in checks against the deployed successor remain outstanding and must not be reported as completed by health, anonymous denials or absent-tenant probes.

Root separately provisions the fresh password into host-only custody, verifies SCRAM privately, installs a role/database-specific hostssl /32 HBA block before broader allow rules, and enables LOGIN. The client must verify the existing server CA and hostname SAN (`PG_SSL=true`, `PG_SSL_REJECT_UNAUTHORIZED=true`, mounted Node CA). Check that an old PG_CONNECTION_STRING or URL sslmode cannot override the successor identity/TLS settings. Those private host/network/container operations are intentionally outside this offline source tool.

Retain the old API image/process/private configuration while production sign-in, fresh membership rejection, cross-tenant denial, schema capability and business/audit atomicity remain unaccepted. Exact identity/TLS and synthetic source checks are separate evidence. The invitation readiness reader and PBX schema diagnostic must use explicit public-schema metadata/resolution checks: this role's catalog-first search path intentionally makes current_schema() equal pg_catalog. Roll back a failed transition by routing to that retained process/configuration first, verifying it, then draining only the successor. Do not drop/demote the old database owner, reset sequences, alter fraud policies or restore the entire database to roll back a login switch. A failed or uncertain COMMIT requires fresh read-only observation, not blind retry.

Execution receipts, exact live container bindings and the detailed action-time handoff remain in the external operator batch directory. They are not repository defaults or proof of deployment. A fresh protected dump/restore receipt is required before separately reviewed live schema operations; historical backup admission clocks cannot be reused.
