# Desktop owned voicemail deletion

The personal inbox remains disabled (`VOICEMAIL_ENABLED=false`). This source adds a reviewed path for future admitted inbox activation; it performs no production deletion or feature activation.

The renderer shows Delete, pending feedback, and Retry delete. Starting a deletion stops the selected player's pending download or local blob before entering IPC. The main process validates its existing sender/frame/URL boundary and accepts only the current session revision and a positive message ID. It owns a parented native confirmation dialog with Cancel as both default and cancellation action; the renderer cannot supply a confirmation bit. Declining keeps the row available. Account replacement during confirmation or completion refuses the old operation.

After explicit confirmation, the privileged provider checks a fresh selected-tenant inbox before calling only `pbx.voicemail.delete` with `{tenantId,id}`. The existing server list filters the authenticated deposit owner and active membership, and deletion independently enforces owner, active membership, tenant, and nondeleted status. List replies must retain the selected tenant identity, supported status, and unique IDs. Missing, foreign, deleted, malformed, or unsupported inbox replies refuse before mutation. The provider accepts only HTTP 200 and the exact tRPC result envelope containing `{success:true}`. False, coerced success, extra result fields, transport errors, or unsupported routes produce generic failure, without upstream errors or credentials. Each deletion preflight and mutation has its own 15-second abort deadline covering headers and body, with a 64 KiB response cap and strict tRPC envelope. A stalled fresh inbox body cancels and releases the pending gate without sending a mutation; an explicit retry repeats confirmation and ownership checks. Ordinary nondestructive inbox requests retain their existing transport behavior.

A deletion advances the provider's inbox generation, blocking concurrent read/audio work for that message and retiring older list/read/audio replies. Successful IDs remain locally retired for that login even if a stale server list repeats them. Replacement accounts get separate state; an old completion cannot retire or unblock their message. Backend mark-read cannot restore a deleted row. The renderer separately binds retained Play/Delete callbacks to account lifetime, revision, tenant, inbox request generation, and current row; it filters retired rows through refresh and ignores late read/deletion replies. One deletion is pending per local inbox at a time. Failed or uncertain transport retains retry feedback; retry still requires a new confirmation and fresh server ownership, never a presumed prior success.

Focused provider tests use injected HTTP responses; renderer and IPC feature-on tests replace only the disabled constant in an in-memory synthetic bundle. The checked-in flag remains false. Tests cover decline, success decoding, missing/foreign/deleted/duplicate rows, account/tenant replacement, duplicate pending requests, stale callbacks, transport/body failures, bounded timeout, concurrent list/read/audio/delete, late audio, and refresh retirement. Existing player tests verify pause/source removal/blob revocation and suppression of late media/read publication.

Passing source tests and bundles establish this source boundary only. Live inbox/media owner admission, server compatibility, deployment, real native confirmation UX, platform playback, and device acceptance remain separate. No backend/schema, license, signing, provider, or release changes accompany this slice.
